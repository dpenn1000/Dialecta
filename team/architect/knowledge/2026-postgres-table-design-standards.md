## Don't Do This, the rules that reach a Supabase app

The wiki page argues from operational experience rather than a spec, so it is
paraphrased here; one phrase is quoted where the wording itself is the argument.

`timestamp` without a time zone stores a reading off a clock with no way to know
whose clock it was; `timestamptz` stores a point in time, which is what almost
every application means. `char(n)` pads short values with spaces instead
of rejecting them, so a length rule enforced by the type silently lies about being
enforced; `varchar(n)` picks an arbitrary ceiling that becomes a production error
the day real data exceeds it. `text` with a `CHECK` where a length matters
gets the constraint without either failure mode. `serial` predates identity
columns and carries, in the page's own words, "weird behaviors that make schema,
dependency, and permission management unnecessarily cumbersome"; `generated always
as identity` (Postgres 10+) is the same autoincrementing behavior without them.
`money` cannot represent a fraction of a cent and rounds in whatever way the
session's locale happens to pick, so `numeric` is the type that commits to
a precision. `NOT IN` against a subquery that can return a null degrades to a scan
the planner cannot rewrite into an anti-join; `NOT EXISTS` is the same query with a
plan.

**Dialecta, checked against the repository.** Grepped `supabase/migrations` for `timestamp`
without `tz`, for `varchar(` and `char(`, and for `serial`/`bigserial`: zero hits
across all six files, all 1,029 lines of the baseline included. Every temporal
column in the schema is `timestamptz`, every string column is `text`, and every
primary key is either `uuid` or a `text` natural key (`admin_capabilities.id`,
`admin_roles.id`, `notification_prefs.member_id`, `reserved_handles.handle`); there
is no `serial` anywhere to migrate off of. Length rules that exist are `CHECK`
constraints on `text` columns (`tier_nominations.note` at 140 characters), matching
the page's own preferred pattern. `money` does not appear; nothing in the 31 tables
prices anything yet. `NOT IN (SELECT` does not appear anywhere in the repository
under a case-insensitive search, migrations or application code, so this rule is
unreached rather than violated. Four of five rules here are already met; the fifth
(identity over serial) has nothing to fix and one live decision waiting, next.

## Primary key choice at scale

A `uuid` primary key generated by `gen_random_uuid()` is a version 4 UUID: 122 bits
of randomness. A B-tree index keeps its keys in sorted order on disk, so a random
key lands at a random leaf page on every insert. Once the working set of hot pages
no longer fits in cache, each insert is a coin flip on whether it also forces a
page split, and the benchmark cited above measured what that costs at 10 million
rows on Postgres 16: version 7 UUIDs, whose leading 48 bits are a millisecond Unix
timestamp, inserted about 35% faster than version 4 into an identical schema, and
the v7 table's own index was roughly 22% smaller because new keys append at the
right edge of the tree instead of splattering across it. A `bigint identity` column
gets the same append-only insert pattern for a third the storage per key, at the
cost of being sequential and guessable, which matters for a public id and does not
for an internal one.

**Version check, done directly against the source.** PostgreSQL 18.0's own release
notes add "UUID version 7 generation function `uuidv7()`... This UUID value is
temporally sortable," alongside a `uuidv4()` alias for the random form, confirmed
by reading the 18.0 release notes page itself rather than a summary of it.
Dialecta's live project is Postgres 17.6, one major behind that function. On 17.6
the choice is: generate v7 client-side before the insert, which most current uuid
libraries already support (an application change), or add a community extension
(a database change). `pg_uuidv7` (PGXN, supports Postgres 13 through 18) is the
obvious candidate, but two open Supabase GitHub discussions (#22015, #22584) are
still asking for exactly this extension with no resolution visible as read, so it
is not confirmed available on Supabase-hosted Postgres. Confirm directly
(`select * from pg_available_extensions where name = 'pg_uuidv7'`) before assuming
either answer.

**What is free now, what gets expensive later.** Changing a column's default
generator, from `gen_random_uuid()` to a v7 generator, from either to
`bigint identity`, costs nothing on a table with a handful of rows: existing keys
keep their shape, only the next insert changes. It stops being free once a table
holds enough rows that its historical v4 keys and new sequential keys share a
B-tree long enough for the split cost above to show up in a query plan, which is
the same size signal `2026-append-only-tables-at-scale.md` uses for partitioning.
The decision is cheapest exactly now, while every one of Dialecta's 31 tables is
small, and it only grows more expensive from here, in the ordinary sense that any
schema change on a populated table does; it never becomes the class of expensive
that a type reinterpretation is, since a default's own history has already been
committed to disk regardless of when it changes.

**Dialecta, by table, hypothesis pending the census.** 26 of 31 tables in the
baseline default their primary key to `gen_random_uuid()`; `types.ts` shows default
expressions directly, so this is one of the categories the baseline file did not
mark LIVE UNVERIFIED. `feed_events`, `axis_events`, and `notifications`, three of
the seven append-only tables the companion note covers, are the highest-write
candidates among the 26 and are on v4 today. Separately, Supabase's own naming
guide (cited below) recommends `identity generated always` as the default primary
key for every table "unless otherwise specified." Dialecta's baseline does the
opposite everywhere. That gap is not automatically a defect: a public discourse
platform has a real reason to keep a comment's id from also announcing how many
comments exist. The divergence from the platform's own documented default is
still worth one written decision, rather than 26 silent repetitions of it.

## Foreign keys

Postgres indexes the referenced side of a foreign key automatically, because that
side must already be a primary key or a unique constraint. The referencing side is
different: "the declaration of a foreign key constraint does not automatically
create an index on the referencing columns," and the docs give the concrete reason
to add one anyway, that deleting or updating a row on the referenced table forces a
scan of the referencing table for matches.

**Dialecta, counted by hand against a stated method.** Grepped the baseline file
for every `references public.` declaration (28 across the file) and checked each
referencing column against every `create index` in the same file, counting a
column as covered when it is the sole indexed column or the leading column of a
composite index or primary key. 10 of 28 are covered. 18 are not: both
non-leading columns of the two admin grant tables' composite primary keys
(`admin_role_capabilities.capability_id`, `profile_admin_roles.role_id`), all three
profile references on `feedback_items`, both `quotes.created_by` and `.updated_by`,
`admin_audit_log.target_id`, `aspirations.declaration_fingerprint_id`,
`profiles.current_aspiration_id`, and, inside the seven tables the companion note
covers, `classifications.comment_id` and `axis_events.comment_id` and
`.classification_id`. This is exact against the baseline file and unconfirmed
against whatever indexes live carries beyond what that file recovered.

**Costed now against later, per the rule in `practices.md`.** At the row counts in
the brief (single digits to a few dozen per table), adding any of the 18 missing
indexes costs nothing and locks nothing; `create index concurrently` on an empty or
near-empty table is instantaneous. The cost that makes this worth fixing before it
is urgent is specific: the day a profile delete needs to cascade or null across
`feedback_items`, `quotes`, or a comment delete cascades through `classifications`
and `axis_events`, each of those is a full sequential scan of the child table to
find matching rows, once per delete, and the scan gets slower every row added
between now and whenever someone notices.

**ON DELETE, already a real pattern, one exception worth naming.** The baseline
consistently cascades on owned content (`comments`, `classifications`,
`axis_events`, `handle_history`, `aspirations`, `fp_snapshots`,
`self_descriptions`) and sets null on attribution columns
(`admin_audit_log.actor_id`/`.target_id`, `quotes.created_by`/`.updated_by`,
`feedback_items`'s three profile references). That split, delete what the row
owns, null what merely attributes it, is the standard shape and it holds across
every table checked. One column breaks it without a marked reason:
`reserved_handles.added_by` carries no `ON DELETE` clause at all, which defaults to
`NO ACTION`, so deleting a profile that once reserved a handle would fail outright
rather than cascade or null. Worth one line confirming that is deliberate.

**NOT NULL, and the identity model underneath it.** Every foreign key column
counted above is declared `not null` except the attribution columns, which is
correct, an attribution to nobody is a legitimate null. The larger version of this
rule is already migrator's, not repeated here: nine tables key on a bare
`member_id text` with no foreign key declared at all, so "required relationship"
is enforced by neither `NOT NULL` nor a constraint on any of them, only by
application discipline. See `team/migrator/knowledge/2026-postgresql-column-type-remap.md`
for the expand-contract path off that, which this note does not re-argue.

## Naming and documentation hygiene

Supabase's own style guide: snake_case throughout, plural table names, singular
column names, a foreign key column named for the singular of its target table plus
`_id` (`user_id` for `users`), names under 63 characters and clear of reserved
words, and "always add an `id` column of type `identity generated always` unless
otherwise specified," the same default the primary key section above found
Dialecta departing from everywhere.

**Dialecta complies on naming, checked against all 31 tables.** Every table name
in the baseline is plural snake_case. Every foreign key column found above follows
singular-table-plus-`_id` exactly: `comment_id`, `article_id`, `profile_id`,
`capability_id`, `role_id`. No violations found by inspection. The one departure
from this cited guide sits in the primary key type covered above; naming itself
complies.

`COMMENT ON` stores a description on a table, column, function, or most other
catalog objects, in the catalog itself, retrievable with `\d+`, `obj_description()`,
or `col_description()`, independent of whichever migration file first wrote it.

**Dialecta has the pattern and has not generalized it.** The 1,029-line baseline
carrying 26 of the 31 tables has zero `COMMENT ON` statements. Every design
rationale in it, why `axis_events` carries no delta column, why `comments` has a
`hardened_at` grace period, why `handle_history` exists at all, lives in `--` SQL
comments inside that one file, readable from git history and from nowhere else.
Two migrations written the same day, after the baseline, already do this the other
way: `20260920000200_profile_claim_tokens.sql` and
`20260920200500_comment_write_identity.sql` carry three real `COMMENT ON`
statements between them, two columns and a table plus two on functions, each
stating exactly the kind of ownership and lifecycle fact the baseline's prose
comments state, and each of them will still answer `\d+ profiles` after nobody
remembers which migration wrote it. Nothing marks the newer pattern as the
expected one, so it exists twice instead of 26 times, from nothing yet saying it
is the standard rather than from any decision against it.

One instance names its own fix. The baseline's comment above `handle_history`
(line 364) says the table's purpose, the SSR `/contributor/<handle>` redirect
path, is stated in "its own `COMMENT ON TABLE`" on live: live already carries a
real comment this file describes and does not reproduce as DDL. A `db reset` from
this baseline today would recreate the table and lose that comment. Recovering the
exact text through the migration-fetch diff the schema-squash runbook already
calls for, and writing it back as a real `COMMENT ON TABLE`, closes the gap in one
statement.

## Implies for

Practice: a table's primary key generator and its foreign keys' indexes are a
decision made once, in the migration that creates the table, not a cleanup pass
after the fact, because the decision is free before rows exist and only grows more
expensive after. Related: `team/migrator/knowledge/2026-postgresql-column-type-remap.md`
covers the far more expensive case, reinterpreting a populated column's existing
values; this note covers the cheap case, choosing a new column's generator before
it has any values to reinterpret. Also related:
`2026-append-only-tables-at-scale.md`, which uses the same now-versus-later size
signal for partitioning and BRIN.
