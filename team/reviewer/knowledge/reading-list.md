# Reading list

Leads, not facts. Every entry below is a lead to verify: confirm the source exists and says
what this line claims before filing a note on it. A lead that turns out to be wrong or missing
is marked `dead` with the reason, which is a result worth keeping.

States: `todo`, `filed`, `dead`.

| State | Lead | Why this agent needs it |
| --- | --- | --- |
| filed | Postgres row-level security: `USING` against `WITH CHECK`, and how multiple policies combine | Check 2 is the one that ships a real breach if it is wrong. The two clauses guard read and write and are easy to confuse. Filed as [2026-postgresql-create-policy](2026-postgresql-create-policy.md). Verified against PostgreSQL 18.6. The lead was right and understated: the larger hazard is that RLS is row level only, so neither clause restricts columns |
| filed | The Supabase RLS guide, including policy performance and the `auth.uid()` pattern | Every policy this repo writes uses it. Knowing the cost shape stops a correct policy that times out. Filed as [2026-supabase-row-level-security](2026-supabase-row-level-security.md). Verified. Carries the `bypassrls` qualifier the lead did not anticipate: the secret key bypasses RLS only when the request carries no user token |
| filed | Postgres `SECURITY DEFINER` functions and default execute grants | A definer function with a public execute grant is a hole that reads as normal code. Worth a note with a concrete example. Filed as [2026-postgresql-security-definer](2026-postgresql-security-definer.md). Verified against PostgreSQL 18.6, including the single-transaction create-and-revoke example. No definer function exists in this repo yet, so the note is a checklist held in advance |
