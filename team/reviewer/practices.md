# Standing practices

A practice is settled until evidence moves it. Confidence is the agent's own read.
Evidence names the file in `knowledge/` that backs it, or `(unsourced)` when nothing does.

| Practice | Confidence | Evidence | Last changed |
| --- | --- | --- | --- |
| Correctness first, and trace one concrete input through the change before judging it | high | `.claude/agents/reviewer.md`; held up on PR 3, where tracing one PATCH request through `articles` found blocker B1 | 2026-09-19 |
| Read the grant layer before the policy layer. Grants decide whether a role reaches the table at all, policies decide which rows, and starting at the policy assumes the answer to the first question | high | `knowledge/2026-supabase-default-grants.md`: "Grants control whether a role can access an object. RLS controls which rows the role can access. Use both controls for every exposed object" | 2026-09-19 |
| Every new table has RLS enabled and policies; ledger tables such as `axis_events` get no update or delete policy | high | `.claude/agents/reviewer.md`; `supabase/CLAUDE.md`; `knowledge/2026-postgresql-create-policy.md` | 2026-09-19 |
| RLS is row level only, so after checking that a policy names the right owner, list the table's columns and ask which of them that owner may write, for `INSERT` as well as `UPDATE` | high | `knowledge/2026-postgresql-create-policy.md`; `knowledge/2025-owasp-asvs-authorization.md` requirement 8.2.3, BOPLA; found blockers B1 and B2 on PR 3, and a fourth path at insert time found afterwards | 2026-09-19 |
| The remedy for a writable column is a table-level revoke followed by a column-list grant. A column-level revoke against a role holding the table-level grant is a silent no-op and is itself a finding | high | `knowledge/2026-postgresql-column-privileges.md`: "the table-level grant is unaffected by a column-level operation" | 2026-09-19 |
| Trace every `dangerouslySetInnerHTML` back to the row and the policy that lets a user write that column, and treat an absent sanitizer in `package.json` as no sanitizer. A sanitizer that runs only in the editor does not count | high | `knowledge/review-checklist.md` row 14; `knowledge/2026-cure53-dompurify.md`; blocker B1 on PR 3 | 2026-09-19 |
| A mitigation is not a mitigation until its configuration is read. Ask whether `script-src` carries `'unsafe-inline'` before crediting a Content Security Policy with anything | high | `knowledge/2026-nextjs-content-security-policy.md`. Written after this agent overclaimed the benefit of a CSP in finding S7 and had to correct it on the record | 2026-09-19 |
| RLS enabled does not mean RLS applies. Ask which role the connection uses, because table owners bypass row security unless `FORCE ROW LEVEL SECURITY` is set | high | `knowledge/2026-postgresql-create-policy.md`, section 5.9: "Table owners normally bypass row security as well" | 2026-09-19 |
| A `security definer` function is a blocker until four things are true: `pg_temp` last in `search_path`, execute revoked from `PUBLIC`, both in one transaction, and the body checked against the RLS it now skips because `postgres` owns the tables | high | `knowledge/2026-postgresql-security-definer.md`; `knowledge/2026-postgresql-create-policy.md` on the owner bypass | 2026-09-19 |
| The `NEXT_PUBLIC_` prefix is the entire client-bundle boundary, so grep the diff for it and read every new name rather than reasoning about imports | high | `knowledge/2026-nextjs-environment-variables.md` | 2026-09-19 |
| A rule the database does not enforce is not enforced. Anything guaranteed only by a client island is reachable by a direct call with the anon key | high | `knowledge/2025-owasp-asvs-authorization.md` requirement 8.3.1 | 2026-09-19 |
| For every write that borrows the service role, name the line that established the originating user's permission before the privilege was borrowed | medium | `knowledge/2025-owasp-asvs-authorization.md` requirement 8.3.3. No pipeline route exists yet, so this is held in advance and untested | 2026-09-19 |
| Code that contradicts a spec is a finding even when it works, and the severity rises when the code writes to an append-only table, because the wrong rows cannot be withdrawn | high | `.claude/agents/reviewer.md` check 3; blocker B3 on PR 3, where `axisDeltasFor` differs from `docs/Dialecta_Axis_Mapping_v1.md` on all six axes | 2026-09-19 |
| Check a claim in a comment or a CLAUDE.md against the code before repeating it. Three claims in PR 3 were wrong in a way no test could catch | medium | PR 3 findings S3, N1 and the stage 2.5 comment at `packages/core/src/resolution.ts:106` | 2026-09-19 |
| Verify the platform assumption before ranking a finding by it, and say so in the report when it is reasoned rather than read | high | PR 3: the `.voiceignore` CRLF concern died on `git ls-files --eol`. The default grants assumption was flagged as unread, then confirmed the same day in `knowledge/2026-supabase-default-grants.md`, which is what the flag is for | 2026-09-19 |
| A platform default that is scheduled for removal is not a remedy. Check whether the change reaches existing objects or only future ones | medium | `knowledge/2026-supabase-default-grants.md`: the grants retire on 2026-10-30 for existing projects, and "Existing tables are not affected... they keep their current grants" | 2026-09-19 |
| The report is a table with severity, file and line, the claim, and the failure scenario, then one line: merge, or not yet | high | `.claude/agents/reviewer.md` | 2026-09-19 |
| Correct an open record by appending, never by editing, so the reasoning stays legible. That includes correcting this agent's own overclaims, which is most of what the appends on record 002 are | high | `exchange/README.md`; two corrections appended to `2026-09-19-002`, one confirming the grants assumption and one withdrawing the stated benefit of a CSP in finding S7 | 2026-09-19 |
| Report the cost of a remedy alongside the remedy. A fix that turns a breach into an indistinguishable 403 is still the fix and the reviewer still owes the reader that sentence | medium | `knowledge/2026-postgresql-column-privileges.md`: `42501` surfaces "as 401 or 403" and has five causes, so a grant denial and a policy bug look identical | 2026-09-19 |
| Never edit. Bash is for read-only git, the test run, the typecheck, and `voice_check.py` | high | `.claude/agents/reviewer.md` | 2026-09-19 |
| Before a finding reaches `builder`, check whether another seat has already argued the same conclusion by a different route. Two independent reasons for one fix belong in the same recommendation, stated as independent, not left as two notes for `builder` to reconcile itself | high | Cross-check requested against `council/security/positions/nextjs-rebuild.md` section 5 found this agent's TipTap advisory and security's client-island argument agree and do not overlap; folded into one instruction in `exchange/open/2026-09-19-002-handoff-pr-3-review.md`'s third correction | 2026-09-20 |
| A framework's own current documentation sample can be wrong for this repo specifically, when a name or an API changed at a version boundary this repo has not crossed. Check the pinned version before quoting a doc's sample verbatim, especially for a renamed file | high | `2026-nextjs-server-actions-authorization.md`: the Next.js Authentication guide's own Proxy sample uses `proxy.ts`, the 16.0.0+ name; `apps/web` is on 15.5.25 and needs `middleware.ts`. Caught only because security's position doc named the same trap independently; corrected in this agent's own note and in checklist row 13b | 2026-09-20 |
| The one automated gate a mandate calls mandatory can still cover none of the bug class that produced the real findings. Read the tool's actual rule list before crediting it with coverage it was never built to have | high | `2026-supabase-database-linter.md`: all 30 documented Supabase linter rules read; none inspects a column-level grant, so the gate that "must be clean" per `supabase/CLAUDE.md` would have said nothing about blockers B1 or B2 | 2026-09-20 |
| A dependency inside its declared semver range is not the same claim as a dependency chosen with a specific advisory in mind. Check whether the resolved version in the lockfile predates or postdates the fix, and say which one is true rather than only that the range is safe today | medium | `2026-tiptap-mergeattributes-xss.md`: GHSA-cp6q-959q-f8rh patched at 3.30.4; `package-lock.json` resolves `@tiptap/core` to 3.31.3, added to the manifest three weeks after the fix shipped. Safe today, safe by luck rather than by policy | 2026-09-20 |
| A "hardening question" left open in the checklist is worth one more primary-source read before it is handed off as still-open. Several close to a definite yes or no rather than staying a judgment call | medium | `2026-postgresql-force-rls-supabase.md` closed checklist row 9b to a settled no: `FORCE ROW LEVEL SECURITY` cannot help on Supabase because the owner role carries `BYPASSRLS` directly, which `FORCE` does not touch | 2026-09-20 |
| Verify a security-advisory citation against the primary registry (GitHub Security Advisories, the vendor's own changelog) before repeating it, even from a source with no track record. A content aggregator can still have the ID right, and the primary source is what makes it citable rather than lucky | high | GHSA-cp6q-959q-f8rh was first seen via a site with no track record checked here ("DailyCVE"); fetched directly from `github.com/advisories` before it went into `2026-tiptap-mergeattributes-xss.md` | 2026-09-20 |
