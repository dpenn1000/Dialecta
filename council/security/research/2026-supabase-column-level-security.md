# Column level security under row level RLS

**Source:** Supabase, "Column Level Security", Supabase Docs, read 2026-09-20, together with the Views section of "Row Level Security", Supabase Docs. https://supabase.com/docs/guides/database/postgres/column-level-security ; https://supabase.com/docs/guides/database/postgres/row-level-security

## Summary

Supabase documents two separate mechanisms for this, not one, and they fit different halves of the problem this seat already found live on this project.

The first is a direct GRANT and REVOKE, scoped to named columns, layered on top of whatever RLS already allows at the row level. The documented pattern revokes the table-level privilege first, then grants back only the columns that should be writable: "revoke update on table public.posts from authenticated; grant update (title, content) on table public.posts to authenticated;" A single column can also be pulled back on its own: "revoke update (title) on table public.posts from authenticated." The one operational trap the page calls out directly: "Restricted roles cannot use the wildcard operator (*) on the affected table," so any select-star or unqualified insert against a column-restricted table now fails, including from PostgREST, and every caller has to name columns going forward. The page's own example is UPDATE-scoped; nothing on it demonstrates a SELECT-column restriction, though the same GRANT and REVOKE syntax applies to SELECT by the SQL standard.

The second mechanism is a view, and Supabase is explicit that a plain view is not safe by default: "Views bypass RLS by default because they are usually created with the postgres user. This is a feature of Postgres, which automatically creates views with security definer... A view over a protected table hands out every row its policies were meant to withhold." The fix, current for Postgres 15 and later, is `create view <name> with(security_invoker = true) as select <query>`, so the view runs as the querying role and RLS is evaluated against them, not against the view's owner. On Postgres before 15, the documented mitigation is different: revoke access to the view from anon and authenticated, or keep it in a schema that is never exposed to the API.

The trap worth naming for a public-profile projection specifically: security_invoker fixes the row-level half, whether RLS still applies, and column narrowing is an ordinary property of the view's own select list, not a separate feature it adds. A security_invoker view that still selects `is_admin` narrows nothing; the column has to be left out of the view's query, same as leaving it out of any hand-written query.

## Implies for Dialecta

- This is the documented shape of the fix already named, but not sourced, in three places: root `CLAUDE.md` ("The fix is column grants or a public-profile view"), `team/migrator/knowledge/2026-live-rls-surface.md`, and this seat's own `2026-live-grant-and-policy-surface.md`. Those three all point at the right fix by reasoning about Postgres generally; this note is the primary-source confirmation of Supabase's own documented syntax for it.
- For `profiles` specifically (`is_admin`, `subscription_tier`, `pact_signed_name`, `order_negotiation_log`, `ghost_member_id` all anon-readable per `team/migrator/knowledge/2026-live-rls-surface.md`), a security_invoker view selecting only the public columns is the better fit of the two mechanisms. `profiles` is read publicly by design (policy "profiles are public to read", `USING (true)`), so the leak is entirely a column problem on SELECT, and a view's column list is a more legible single place to see what is public than REVOKE statements scattered across migrations.
- For the other finding, the write-side owner-writes-own-row gap on `comments.final_tier`, `comments.status`, `articles.status`, and `aspirations.expires_at` (`team/reviewer/knowledge/2026-postgresql-create-policy.md`, blockers B1 and B2), the GRANT and REVOKE mechanism is the fit, not a view: these are UPDATE policies on tables contributors need to write to directly, and the documented pattern, revoke update on the table then grant update back on the named allowed columns, matches this case almost exactly as Supabase wrote the example.
- The wildcard trap applies immediately once either fix lands. Any code in `apps/web` (or a future admin surface) that does `select('*')` or an unqualified insert against `comments`, `articles`, `aspirations`, or a narrowed `profiles` view breaks the moment the column grant exists. Audit `apps/web/src` for `select('*')` before shipping either fix, not after.
- Note for whoever applies this: it is a migration, same as the write policies that created the underlying finding. `council/security/positions.md` already holds the position that any grant-tightening migration has to land before or with the policy migration that depends on it, never after, and the same ordering risk applies here symmetrically: revoking SELECT on `is_admin` has to ship with or before anything that starts relying on `profiles` being column-safe to read.
