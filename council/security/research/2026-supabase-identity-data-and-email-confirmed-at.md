# identity_data Contents and email_confirmed_at Gating

**Source:** Supabase, "supabase/auth" (formerly GoTrue), branch `master` at commit `2e9ce6c8` (tag `rc2.198.0-rc.11`), read 2026-09-20. https://github.com/supabase/auth

## Summary

**Question A, what lands in `identities.identity_data`.** Normalized, not verbatim and not a hand picked subset of the raw response. In `internal/api/external.go`, `createAccountFromExternalIdentity` builds it with `identityData = structs.Map(userData.Metadata)`, where `userData.Metadata` is a `*provider.Claims`. `models.NewIdentity` (`internal/models/identity.go`) stores that same map as `identity_data` verbatim, and separately copies its `email` key, if present, into the `identities.email` column. The `Claims` struct (`internal/api/provider/provider.go`) is modeled on OIDC standard claims: `iss`, `sub`, `aud`, `iat`, `exp`, `name`, `family_name`, `given_name`, `middle_name`, `nickname`, `preferred_username`, `profile`, `picture`, `website`, `gender`, `birthdate`, `zoneinfo`, `locale`, `updated_at`, `email`, `email_verified`, `phone`, `phone_verified`, plus a `custom_claims` object and four deprecated aliases (`full_name`, `avatar_url`, `slug`, `provider_id`, `user_name`). Every field but two carries `omitempty` on its `structs` tag, so it is dropped from `identity_data` entirely when zero valued. `email_verified` and `phone_verified` are the two exceptions: they carry no `omitempty`, so they are always present, `true` or `false`, never absent.

That last detail matters because each provider's `GetUserData` populates two structures independently: `UserProvidedData.Emails` (the list `DetermineAccountLinking` and `Confirm` actually read, see the earlier note on this list's per-provider honesty) and `UserProvidedData.Metadata` (the `Claims` that becomes `identity_data`). Verified verbatim, file and line: `facebook.go:81-116`, `x.go:92-137`, `twitter.go:97-121`, `github.go:81-114`, `gitlab.go:72-110`, and `discord.go:73-113` all set `Emails[].Email` and `Emails[].Verified`, and none of them sets `Metadata.Email` or `Metadata.EmailVerified` in the same function. For an identity created through any of these, `identity_data` carries `"email_verified": false` (the Go zero value) and no `email` key at all, and `identities.email` stays unset too, regardless of what `Emails[].Verified` said at sign in. `google.go`'s REST fallback path syncs both (`Email: u.Email, EmailVerified: u.IsEmailVerified()`, lines 121 to 127), but that function's own comment says the fallback is legacy, for when Google does not return an ID token, which it says "appears to always be the case," meaning the fallback does not run in practice. Google's real path, `parseGoogleIDToken` in `oidc.go`, does not sync `Metadata` either. `keycloak.go`, `custom_oauth.go`, and the unrecognized issuer fallback `parseGenericIDToken` in `oidc.go` do sync both, because those three read the whole claims object into `Metadata` first and derive `Emails` from it, the reverse order from the rest.

One place this desync has an already written, internal consequence: `internal/models/identity.go` defines `func (i *Identity) IsEmailVerified() bool`, body `verified, ok := i.IdentityData["email_verified"].(bool); return ok && verified`, with its own doc comment reading "returns true only when identity_data contains email_verified: true. A missing key is treated as unverified." `internal/models/user.go`'s `UpdateUserEmailFromIdentities` calls this method to decide whether a user stays confirmed after their primary identity changes, on identity removal or unlink: when `primaryIdentity.GetEmail() == "" || (!primaryIdentity.IsEmailVerified() && !mailerAutoconfirm)`, it sets `u.EmailConfirmedAt = nil`. For a user whose remaining identity is Facebook, X, GitHub, GitLab, Discord, or Google's ID token path, `IsEmailVerified()` reads `false` off a key that was never honestly populated, and this code un-confirms them.

**Question B, `email_confirmed_at`.** Gated, not unconditional on OAuth. `func (u *User) Confirm(tx *storage.Connection) error` in `internal/models/user.go`, line 524, sets `u.EmailConfirmedAt = &now` and writes it with `tx.UpdateOnly(u, "confirmation_token", "email_confirmed_at")`; it also mirrors `"email_verified": true` into `raw_user_meta_data`, a third, separate location carrying a copy of the same signal. The OAuth sign in call site is `internal/api/external.go` line 426, inside `createAccountFromExternalIdentity`, in this shape:

`if hasEmails && !user.IsConfirmed() { RemoveUnconfirmedIdentities(...); if decision.CandidateEmail.Verified || config.Mailer.Autoconfirm { ...; user.Confirm(tx) } else { send confirmation email, or return ErrorCodeProviderEmailNeedsVerification } }`

`decision.CandidateEmail.Verified` is the exact same field, from the exact same `provider.Email` in the `Emails[]` list, that gates `DetermineAccountLinking`. Not `Metadata.EmailVerified`, not `identity_data`. It is honest for Google, GitHub, GitLab, Discord, Keycloak, Azure, and any generic or custom OAuth or OIDC provider, and hardcoded to `true` regardless of the provider's own claim for Facebook, X, legacy Twitter, and Apple's native ID token path, per the earlier note on this codebase. `Confirm` has five other call sites, each checked directly: `admin.go` twice, an operator action; `signup.go`, password signup, gated by its own autoconfirm setting; `verify.go` twice, a clicked confirmation or recovery token; `identity.go`, the authenticated manual link endpoint; and one more each inside `external.go` and `user.go`, for invite acceptance and email change confirmation, both gated on the user having proven control of that specific inbox by a route other than the OAuth claim itself. None of the six sets `email_confirmed_at` unconditionally on the fact of an OAuth sign in alone.

So B is gated, which makes `email_confirmed_at` a single, provider-independent place to check, computed in one place rather than parsed per identity. But the condition it is gated on is the same `Emails[].Verified` bucketing from the earlier note, not an independent re-verification: a Facebook or X sign in confirms the user exactly as readily as a Google one does, because Supabase's own provider code, not Facebook or X, is what marked the email verified.

## Implies for Dialecta

- Check `auth.users.email_confirmed_at`, never `auth.identities.identity_data->>'email_verified'`, for any control that needs to know whether a sign in's email was treated as verified. The identity level field is unreliable by construction for Facebook, X, GitHub, GitLab, Discord, and Google's real ID token path, confirmed from the provider source itself, not inferred.
- `email_confirmed_at` is one column and behaves the same for every provider procedurally, but it inherits the exact per-provider trust gap from the automatic linking note: it does not mean Supabase re-verified the email, it means the specific provider's code in `internal/api/provider/` asserted `Verified: true`. Google, Facebook, and X all set `email_confirmed_at` identically on first sign in; only Google's assertion is independently checked against a real claim.
- If Dialecta ever adds a feature to remove or unlink a provider identity, read `UpdateUserEmailFromIdentities` in `internal/models/user.go` before shipping it. A contributor who signed up with Facebook or X and later unlinks a second, since removed identity can be silently moved to `email_confirmed_at = NULL` by this function reading a stale `identity_data.email_verified`, which would then block them from anything gated on confirmation until they reconfirm.
- Do not build anything on `identity_data.email` either. It is absent, not just unverified, for the same provider list, and the `identities.email` column is only populated when that key exists.
