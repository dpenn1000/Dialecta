# server-only and the React Taint API

**Source:** React (Meta), "experimental_taintObjectReference", react.dev reference docs, read 2026-09-20, together with Next.js's "taint" configuration reference and the `server-only` section of the Next.js Data Security guide. https://react.dev/reference/react/experimental_taintObjectReference ; https://nextjs.org/docs/app/api-reference/config/next-config-js/taint ; https://nextjs.org/docs/app/guides/data-security

## Summary

Two different maturity levels are being asked about together, and they are not the same. `server-only` is a plain, stable npm package. Marking a module with `import 'server-only'` is a build-time guarantee, not a runtime check: per the Next.js docs, "This ensures that proprietary code or internal business logic stays on the server by causing a build error if the module is imported in the client environment." Next.js implements the enforcement itself and does not run the package's own code: "Next.js handles server-only imports internally. The contents of these packages from NPM are not used." Nothing about this is experimental, and it is already the recommended default for any module that touches a database or a secret.

The Taint API is a different story and is still experimental in both React and Next.js as of this read. React's own reference page states it plainly: "This API is experimental and is not available in a stable version of React yet," and the only documented way to try it is "upgrading React packages to the most recent experimental version." Next.js's own config page carries the same warning in its own words: "This feature is currently experimental and subject to change, it's not recommended for production." One nuance resolves an apparent conflict between those two statements: turning on `experimental.taint` in `next.config.ts` does not require manually installing `react@experimental`. The Next.js docs say the flag "also enables the React experimental channel for app directory" on its own, and additionally taints `process.env` as a whole object.

The limits matter as much as the feature. React's docs state them as a caveat, not a footnote: "Tainting an object doesn't prevent leaking of every possible derived value... Using data from a tainted object (e.g. `{secret: taintedObj.secret}`) will create a new value or object that is not tainted." Next.js's own worked example confirms the same failure mode for values: passing `systemConfig.SERVICE_API_KEY` directly is blocked, but a template string built from it, `` `version::${systemConfig.SERVICE_API_KEY}` ``, is not. Both docs land on the same recommendation: taint is a second layer, not a substitute for simply not returning the sensitive field from the data access function in the first place.

## Implies for Dialecta

- `apps/web` has no `server-only` imports yet. Neither `apps/web/src/lib/supabase/server.ts` nor `client.ts` uses it (confirmed by reading both files 2026-09-20). Any new module that queries `profiles` directly, or wraps the Supabase service role key rather than the anon key, should start with `import 'server-only'` on day one. This part carries no experimental risk and no version gate.
- Do not reach for the Taint API as the fix for the `profiles` column exposure. Next.js's own words are that this is "not recommended for production," and the underlying finding (`is_admin`, `subscription_tier`, `pact_signed_name`, `order_negotiation_log`, and `ghost_member_id` all readable by the anon key, per `team/migrator/knowledge/2026-live-rls-surface.md` and `2026-live-grant-and-policy-surface.md`) is a database grant problem. Taint would only catch a Server Component accidentally spreading the whole profile row into a Client Component prop, one specific mistake among several, and would not touch the anon key reading those columns directly over the Data API. See `2026-supabase-column-level-security.md` for the actual fix.
- If a Data Access Layer is built for `apps/web` per `2026-nextjs-server-actions-authorization.md`, that is the natural place to enable taint later as a second layer once the column grants or a public profile view are in place, not as a replacement for them. Enabling it turns on the React experimental channel for the whole app directory, which is a bigger decision than it looks and is worth its own line in a backlog item rather than a drive-by flag flip.
