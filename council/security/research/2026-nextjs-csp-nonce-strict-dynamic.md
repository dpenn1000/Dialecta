# CSP nonces, strict-dynamic, and the dynamic rendering cost

**Source:** Next.js (Vercel), "Guides: Content Security Policy (CSP)", official documentation, read 2026-09-20 (version 16.3.5 snapshot, last updated 2026-03-20), together with MDN, "CSP: script-src", the strict-dynamic section, read 2026-09-20. https://nextjs.org/docs/app/guides/content-security-policy ; https://developer.mozilla.org/en-US/docs/Web/HTTP/Headers/Content-Security-Policy/script-src

## Summary

This extends `2026-nextjs-security-headers-csp.md` rather than repeating it, with the two specifics that note left open: what strict-dynamic does, and why unsafe-inline sits in the docs' own example.

strict-dynamic is not a Next.js invention and Next.js's guide does not explain it inline, so MDN is the primary source for the mechanism itself. MDN states it exactly: "the trust explicitly given to a script present in the markup, by accompanying it with a nonce or a hash, shall be propagated to all the scripts loaded by that root script. At the same time, any allowlist or source expressions such as 'self' or 'unsafe-inline' will be ignored." In practice, a nonced script tag is trusted, and anything that script goes on to load or inject is trusted by inheritance, while a plain host allowlist stops being honored at all once strict-dynamic is present. This is exactly the shape of a Next.js production bundle, where one nonced script tag kicks off loading the framework runtime and page chunks dynamically. Without strict-dynamic, each of those chunk URLs would need its own allowlist entry or hash; with it, trust flows from the one nonced root script.

unsafe-inline's presence is not a strength-reducing accident. It appears exactly once in the guide, in the section titled "Without Nonces," the simpler alternative path for an app with no inline scripts to protect: setting the header directly in `next.config.js` with no Proxy involved. That path's own example reads `script-src 'self' 'unsafe-inline'`, and unsafe-inline there is the direct cost of skipping the nonce machinery, not a recommended production value. The nonce path never includes unsafe-inline in production; it appears only in the development-only branch of that same code sample, alongside `'unsafe-eval'`, both scoped to a development check.

The tradeoff is stated as a hard requirement, not a suggestion: "you must use dynamic rendering to add nonces," because a nonce that does not change per request is not a nonce, and a static page has no request to generate one from. The guide is specific about what that costs: static optimization and Incremental Static Regeneration turn off for any page carrying a nonce, and Partial Prerendering is flatly incompatible with nonce-based CSP, "since static shell scripts won't have access to the nonce." The guide's own experimental alternative, Subresource Integrity hashing, exists specifically to let a site keep static generation while still refusing unsafe-inline, at the cost of being unable to handle scripts generated at runtime.

## Implies for Dialecta

- `apps/web/next.config.ts` has no `headers()` function today (confirmed 2026-09-20, same reading as `2026-nextjs-security-headers-csp.md`), and there is no `middleware.ts` or `proxy.ts` in the app at all. The existing note's recommendation to start with the simpler `next.config.js` path stands: nothing in `apps/web` renders inline scripts yet, no analytics, no tag manager, so unsafe-inline's cost is not being paid for nothing today. It would be adopting a real weakness ahead of any actual need for it.
- The moment a reason to go nonce-based shows up (the Tiptap editor rendering stored HTML is the one the existing note already flags), remember two things that note did not have space for: the policy needs strict-dynamic, not a plain host allowlist, if Next.js's own chunked script loading is going to work under it, and every page that carries the nonce becomes dynamically rendered, a real cost on pages that would otherwise be static, not a formality.
- On `next@15.5.25` the file is `middleware.ts`, exporting a function named `middleware`. Every code sample on the current CSP guide is written as `proxy.ts` exporting `proxy`, which is Next.js 16 naming that did not exist before 16.0.0 (see `2026-nextjs-middleware-cve.md`). Copy the logic, rename the file and the export, or it never runs.
- Whoever builds this should read `2026-nextjs-security-headers-csp.md` first for the baseline header set and the OWASP Validator verification step, then this note for the nonce path specifically. Keep both rather than merging them; the simpler path is still the right starting recommendation.
